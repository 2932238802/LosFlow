## 一句话结论

LosFlow 里 Claude Code 的派单链路是「只读回执」：`/api/task/dispatch` 跑完只回写 `sessionId`，**从不改任务状态**；而任务表 `Vesta.tasks.json` 的 `status` 是驾驶舱唯一的进度真源（阶段条、进度条、已完成页、自动整理全靠它）。于是任务天生只有两种可见态——「执行中」和「待派单」，跑完就退回「待派单」，人没有任何按钮能把它推到「已完成」。

## 复现步骤

1. 「任务」页写标题 → 加入池 → 推入，得到 `#N`（`status = todo`），文档同步那条先入队。
2. 展开卡片点「发给 Claude Code（新会话）」，「终端」页看到思考 / 命令 / 输出 / 回执。
3. 回执状态 `ok`，终端静止，侧栏「CC 执行中」消失。
4. 回「任务」页：徽标从「Claude 执行中」变回**「待派单」**，进度条停在 10%（或文档同步完成后的 30%）。
5. 卡片里能点的只有：优化提示词 / 继续发给 Claude Code / 看终端 / 终止 / 删除——**没有「完成」「验收」**。
6. 「已完成」页没有它；侧栏「已完成」计数为 0；阶段条不前进到 ⑧；自动整理计数不增加。

对照 `docs/api.md` 的写接口清单，确认没有任何状态写入口。反过来，能改 `status` 的只有两处，都不在驾驶舱里：

- `agent/wb-bridge/server.mjs` 的 MCP 工具 `next_task`（写 `doing`）、`report_task`（写 `done`/`blocked`）——只服务 WorkBuddy；
- `agent/taskboard.ps1 -Set <id> -Status done`——手工命令行，界面上没有。

## 根因

1. **语义缺口**：「派单执行完」≠「任务完成」。前者是 CC 回执事实（`ok/denied/error/timeout/unparsed`），后者是人验收后的判断。现有模型只有前者，没有承载后者的状态和入口。
2. **单向数据流**：任务是「池子 → 任务表 → 终端」单向派出去，终端的结果没有回流的通道（只有日志，不进状态）。
3. **状态机缺环**：`todo → doing → done` 里 `doing` 在 CC 链路根本没被写过（只有 WB 的 `next_task` 会写），`done` 只有 WB 会写。CC 链路实际上是 `todo → todo`。

## 影响

- 流水线断在最后一步：README 写的「回填 → 台账 + 腾讯文档任务表 → 归档」中，**回填没有入口**，只能去命令行敲 `taskboard.ps1`。
- 「任务」页会越用越像「待派单堆积」，看不出哪些其实已经跑完等验收，人得靠记忆区分。
- 「自动整理主表」这个功能等于死代码：`seenDone` 永远空，阈值永远到不了。
- 任务跑完后的证据（回执 `result`、轮次、花费）只留在台账和 `task-journal.md`，没有写回任务表的 `evidence` 字段。

## 采用方案：终端里标记完成 + 类型 / 区域（杰哥 2026-11-13 定）

**核心**：在「终端」页给每条会话一个「标记 Claude Code 工作已完成」的动作；标记时顺手标注这条会话干了什么（类型）和动的是哪块（区域）。任务状态由这个标记推进，不靠猜回执。

**类型 → 区域**：

| 类型 | 动到哪 | 说明 |
| --- | --- | --- |
| 开发（dev） | 代码区 | 改仓库代码，区域默认任务卡上的 `repo` |
| review | 文档区 | 只写评审结论，落文档；文档区在标记时交互式指定 |
| Plan | 文档区 | 只写方案 / 计划，落文档；同上交互式指定 |

**交互流程**：

1. 终端卡头部（`App.vue:737` 一带）加「标记完成」按钮；CC 跑完、人核对后点它。
2. 弹出小面板：类型（开发 / review / Plan）、区域（代码区 / 文档区）、证据（预填最后一次回执的 `result` 摘要 + 轮次 + 花费）。
3. 选「文档区」时给路径选择：默认任务 `repo` 下的 `docs/`，可逐级改（复用「项目」那套目录浏览，或直接填路径）。
4. 确认后写任务表：`status=done`、`evidence`、`workType`、`area`、`finishedAt`；终端卡出现角标「已完成 · 开发 · 代码区」；任务页卡片同步。
5. 阶段条 / 已完成页 / 自动整理按现有逻辑自然走（全 `done` → ⑧）。
6. 标错了就「重新打开」：`status` 回 `todo`，证据和上一次回执保留。

**数据字段**（`Vesta.tasks.json` 增字段，旧任务缺省不报错）：

| 字段 | 值 |
| --- | --- |
| `workType` | `dev` / `review` / `plan` |
| `area` | `{ kind: "code" \| "docs", path: string }` |
| `finishedAt` | 时间戳 |

**接口**：

```
POST /api/task/status   { id, status: "done" | "todo", workType?, area?, evidence? }
```

带 `x-dash: 1`。`done` 时顺带 `docSync` 入队一条回填行（写明类型 + 区域路径），`checkAutoCleanup` 的计数自然累加。

**为什么不全自动**：回执 `ok` 只说明 Claude 跑完了，不说明它改对了地方；「类型 + 区域」是给人看、给台账看的，必须由人确认。

**与自动待验收的关系**：这一版是人工确认版。之后若想防漏，再叠一层「回执终点 → `reviewing` 自动待验收」，两者不冲突。

## 候选方案（初版，供对照）

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 纯手动 | 终端卡 + 任务卡各加「标记完成」，`POST /api/task/status { id, status, evidence }` | 改动最小，人说了算 | 靠自觉；仍看不出跑完了 |
| B 自动待验收 + 人工确认 | 派单终态落 `reviewing`，验收通过才 `done` | 不会漏、和阶段推断兼容 | 多一个状态 + 迁移旧数据 |
| C 让 CC 自报 | 提示词要求输出 `{ "status": "done", "evidence": "..." }` 自动 `done` | 全自动 | 回执不可信，仍要人看 |

## 验收标准

- 终端跑完不点任何东西 → 任务状态不变（人工判断不被绕过）。
- 点「标记完成」选 开发 / 代码区 → 任务进「已完成」；`evidence` 含回执摘要与区域；全部完成时阶段条到 ⑧、自动整理计数 +1。
- 选 review / Plan + 文档区并指定路径 → 「已完成」页能看到类型和文档路径。
- 终端卡角标与任务卡状态一致，刷新后仍在（读任务表，不是前端内存）。
- 「重新打开」→ 回 `todo`，上一次证据不丢。
