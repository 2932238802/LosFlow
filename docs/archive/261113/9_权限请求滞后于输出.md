## 一句话结论

**不是面板慢，是权限本身被做成了"事后报告"。** 现在只有等 `claude -p` 整个跑完，才从回执的 `permission_denials` 里反推出"刚才被拒了几条"，再写进 `approvals.json`；所以人看到的永远是已经结束的事故，而"批准"只能把整条任务重派一遍，等于同一份上下文再买一次。

要消掉滞后，必须把"问人"接进 Claude Code 的权限链路：用 `--permission-prompt-tool` 指向 LosFlow 自己的本地 MCP 工具，在工具真正执行**之前**同步问右侧栏，批准/拒绝当场回到那一次 run 里——不需要重派。

## 1. 现象：两个真实样本

### 样本 A：2026-11-13 19:03 的 Vesta 只读巡检（run `20261113-190359-a81c97`，任务 #8）

| 时刻 | 发生了什么 | 证据 |
| --- | --- | --- |
| 19:03:59 | 派单开跑 | 台账 `at` / `running.json` |
| 19:04:08 | **第一条 Bash 就被拒**（"This Bash command contains multiple operations… requires approval"） | `data/streams/20261113-190359-a81c97.jsonl` 第 292 行，`timestamp=11:04:08.779Z`（=19:04:08），`tool_result_meta[].permission_decision={decision:"reject",source:"config"}` |
| 19:04:08 → 19:10:36 | Claude 反复绕路，被拒 9 条 Bash，跑了 **165 轮** | 台账 `turns=165`、`denials=[Bash ×9]` |
| 19:10:36 | 跑完，回执 `status=denied`，**花费 $4.3455** | 台账 |
| **19:10:37** | 授权卡片才出现在 `approvals.json` | `approvals.json` 该条 `at` |
| 19:10:41 | 点「批准」→ 写 allowlist → 自动重派 | `approvedAt` / `retriedAt` |
| 19:10:42 | 重派**直接失败**：`Daily cap reached: spent ¥9.421 today, cap ¥2.000` | `.tmp/claude-retry-ap-20261113-190359-a81c97.log` |

滞后 **6 分 37 秒**；而真正的卡点发生开跑后 **第 9 秒**。

### 样本 B：同日 16:50 那次（run `20261113-165004-c3475c`）

开跑 16:50:04，授权记录出现在 16:56:19——滞后 **6 分 15 秒**，同样是 9 条 Bash 被拒。

### 这两个样本说明了什么

- 面板上的"等你批"不是请求，是**事故报告**：它诞生于进程结束之后（`approvals.json` 的 `at` 比 run 结束晚 1 秒）。
- 这 6 分钟里 Claude 并没有"卡住等人"，它在**想办法绕**（换命令、拆步骤、改写），既烧钱也偏离任务；你在面板上看到的批准，批的是"下一次重跑"，不是"刚刚那一步"。
- 批准并不便宜：它触发一次**整单重派**（`approvals.mjs:71` → `retryDispatch`），上下文重买一遍。样本 A 连这次重派都被日限额拦下了——也就是说"批准"这个动作今天甚至没换来任何执行。

```
"A variable in braces in this command can't be checked before it runs; under the read block
 (permissions.blockReadsOutsideWorkingDirectories) a command the shell parser cannot analyze
 asks the person"
```

## 3. 为什么这不是"小毛病"

1. **时间**：卡点在第 9 秒，人 6 分钟后才知道。这 6 分钟 Claude 在绕路，结论质量下降（样本 A 的回执里明确写着哪些命令"没跑成"）。
2. **钱**：一次 denied 的 run 花了 $4.35（165 轮）；批准再整单重派等于再买一遍同样的上下文。今天的免费额度被这一条就吃穿了（¥9.42 vs ¥2 日限）。
3. **语义错位**：人以为自己批的是"当前这一步"，实际批的是"下一次整单"；被拒的那一步早就过去了，批准永远追不上。
4. **信任**：面板是这套驾驶舱的核心卖点（README：「撞权限墙 → 右侧授权栏批准」）。现在它只报丧，不救火。

---

## 4. 目标与非目标

**目标**

1. 请求在**将要执行之前**出现（目标 <3 秒），而不是跑完之后。
2. 批准/拒绝**当场生效**：批准则同一次 run 继续执行该命令；拒绝则同一次 run 收到拒绝理由继续跑。**不重派、不重买上下文。**
3. 卡片给足上下文：哪条任务、哪个 run、要执行什么、建议放行哪条规则、还剩多少秒超时。
4. 不破坏现有链路：成本、台账、stream 回放、会话续接、终止、allowlist 全部保持；未启用 live 审批时退回今天的行为。
5. 失败可见：服务不可用/超时要明确降级为"拒绝"，不能让 run 挂死。

**非目标**

- 不做逐段命令编辑/改写（继续用 Claude Code 自己的规则语法）。
- 不改 Claude Code 的权限模型，只把它的"问人"接到我们这边。
- 不做远程/多机审批（本机右侧栏）。
- 不在这一版里统一 WSL / Windows 两边的授权语义差异（见文档 7 的 env 分流，这里是同一条链路）。

## 6. 选定方案 A

### 6.1 时序

```
claude-dispatch.ps1  →  claude -p … --permission-prompt-tool mcp__losflow-approval__approval_prompt
                                   │
                                   │ 某条调用需要授权
                                   ▼
                        agent/approval-mcp.py（stdio MCP，跑在 WSL / Windows 里）
                                   ├─ 写 data/live/<id>.req.json
                                   └─ 每 200ms 轮询 data/live/<id>.res.json
                                   ▲
server/approvals.mjs  ── 300ms 扫 data/live ──┘
   ├─ approvals.json 追加 {status:"waiting", live:true, runId, taskId, tool, cmd, suggested}
   ├─ SSE /events/losflow 推 {kind:"approval", …}      → 右侧栏 1s 内出现
   └─ 人点「只批这次」→ 写 <id>.res.json {decision:"allow"}（不写 allowlist、不重派）
                                   │
        approval-mcp.py 读到 res → 返回 {"behavior":"allow","updatedInput":<原样>}
                                   │
                          同一次 run 继续执行该命令
```

超时（默认 45–60 秒，见风险 2）→ 工具返回 `{"behavior":"deny","message":"等待人工授权超时，按拒绝处理；不要换个写法重试"}`。

### 6.2 MCP 工具契约

- 服务名：`losflow-approval`；工具名：`approval_prompt`；全名 `mcp__losflow-approval__approval_prompt`。
- **入参**（Claude Code → 工具）：`{ tool_name, input, tool_use_id, permission_suggestions }`。字段名已在 2.1.323 的可执行文件里核对到（`[wireFrameShape] can_use_tool request` 的校验串包含 `permission_suggestions`），与 SDK 的 `canUseTool(toolName, input, {suggestions})` 同源。
- **返回**（工具 → Claude Code，JSON 字符串）：
  - 允许：`{"behavior":"allow","updatedInput":<input 原样>}`
  - 拒绝：`{"behavior":"deny","message":"<人写的理由>"}`
- **注意**：`updatedInput` 必须满足该工具的输入 schema，否则 Claude Code 会以 `permission_updated_input_invalid` 拒掉并让模型重来（2.1.323 里有这条错误分支）。所以"批准"就**原样回传 input**，不要顺手改字段。
- **兜底**：工具内部异常 / 文件读写失败 → 返回 deny + "LosFlow 授权服务不可用"，让 run 继续而不是挂死。

### 6.3 文件握手协议（为什么不用 HTTP）

`data/live/`（git 忽略，随 `data/` 一起清理）

```json
// <id>.req.json  —— approval-mcp.py 写
{ "v":1, "id":"lv-20261113-190412-7f3a", "at":"2026-11-13 19:04:12",
  "runId":"20261113-190359-a81c97", "taskId":"8",
  "tool":"Bash", "input":{"command":"npm run verify"} ,
  "suggestions":[{"type":"addRules","rules":[{"toolName":"Bash","ruleContent":"npm run verify:*"}],"behavior":"allow","destination":"localSettings"}],
  "cwd":"/home/losangelous/LosAngelous/Vesta" }

// <id>.res.json  —— server 写
{ "v":1, "id":"lv-20261113-190412-7f3a", "decision":"allow",
  "message":null, "rules":[], "decidedAt":"2026-11-13 19:04:35", "decidedBy":"dashboard" }
```

- 原子写：先写 `<id>.tmp` 再 `rename`，避免读到半截 JSON。
- 谁写谁清：`approval-mcp.py` 收尾时删 req/res（或移到 `data/live/archive/` 留痕）；server 只读 req、只写 res。
- 为什么用文件：WSL→Windows 的 `127.0.0.1` 是否通取决于 `networkingMode`（NAT / mirrored），`/mnt/d` 两种情况都稳；也不用新开监听端口、不用碰防火墙。目录本身就在 `data/` 里，符合"data 是唯一真源"的现状。

### 6.5 边界与失败处理

| 情况 | 处理 |
| --- | --- |
| 调用本就在 `--allowedTools` / `acceptEdits` 命中范围内 | 不会经过这个工具，不会打扰人（这是它比 hook 方案好的关键） |
| 一次 run 里多次请求 | 按 `id` 排队；`-p` 单会话基本串行；子 agent 并行也各有 id |
| server 重启 / 面板关掉 | 内存无待决表 → 启动时重扫 `data/live`；MCP 侧超时兜底为拒绝 |
| 人一直不点 | 超时自动 deny，卡片标「已超时」，run 继续 |
| 人点「拒绝」 | deny + 明确理由："人工拒绝；不要换个写法重试，先向用户说明"——避免它连撞 |
| 想放行同类命令 | 「批准并记住」→ 写 allowlist（沿用现有规则格式），下次直接命中 allowedTools，不再问 |
| 想停 | 卡片保留「终止这次运行」，走现有 `/api/run/stop`，杀完再按需重派 |

## 7. 降级 / 止血方案 C（半天）

A 没落地前（或机器上 python3 不可用）先用这个：

1. `server/events.mjs` 在 `readRunRounds` 配对 `tool_use` / `tool_result` 的地方（358-400 行、517-533 行的 `emitRaw` 路径）判断：`is_error=true` 且 `tool_result_meta[].permission_decision.decision === "reject"`。
2. 用 `tool_use_id` 找到那条 `tool_use` 的命令，**立刻**写一条 approvals（`live:false, midRun:true`），按 `tool_use_id` 去重，SSE 推。
3. 卡片标「这次运行还在继续」，给「终止并重派」。

收益：从 6.5 分钟缩短到 ~1 秒；批准仍然要重派（因为那次工具已经被拒了）。
代价：run 还在烧钱，只是人能早点决定要不要停。

## 8. 验收标准

1. 一条不在 `allowedTools` 里的 Bash：run 开始后 **3 秒内**右侧栏出现卡片，含任务名、runId、命令原文、建议规则。
2. 点「只批这次」：**同一次 run 继续**，该命令真实执行（流里该 `tool_use` 的 `tool_result` 为成功），回执 `permission_denials` 不含它，台账只有一条 run。
3. 点「拒绝」：该 `tool_result` 是错误且带拒绝语，run 继续，不重派；`approvals.json` 状态 `rejected`。
4. 超时（默认 45–60s）不答：自动拒绝，卡片显示「已超时」，run 不挂死。
5. 关掉 live 审批（配置回退）：今天的行为不变（跑完入队 + 手动批准 + 重派）。
6. 历史 `approvals.json`（无 `live` 字段）仍能正常显示 / 批准 / 拒绝。
7. `npm run smoke` 绿；动前端后 `npm run build` 绿。

## 9. 风险与待确认

1. **`--permission-prompt-tool` 在 2.1.323 是隐藏 flag**：`--help` 不列它，但可执行文件的 flag 表里有（`--permission-prompt-tool`），且 `--permission-prompts host` 的说明直接指向它（"the SDK host or --permission-prompt-tool"）。**实施第一步必须做一次最小验证**：写一个只打印入参、固定返回 deny 的 MCP，跑一次真实 run，确认①工具被调用、②返回 allow 后命令真的执行、③返回的 JSON 形状被接受。
2. **MCP 工具调用可能有 60 秒上限**（未确认）。所以默认等待设 **45–60s**，不要设 120s；UI 倒计时按实际值显示。
3. **WSL 里要有 python3**（Ubuntu 默认自带；本机 Windows 侧已确认 Python 3.13）。没有就在 preflight 直接报错，不写 `running.json`、不花钱。
4. **fs.watch 跨 9p 可能收不到事件**：server 侧用 300ms 轮询兜底（本地小目录，开销可忽略）。
5. **与 `-Mcp` 并用**时，`--strict-mcp-config` + `--mcp-config` 的合并顺序要实测（任务需要 context7 等时）。
6. **提示注入**：命令原文来自模型，卡片按纯文本展示（现有 `cmdText` 已是纯文本），不要渲染 HTML；批准永远是人的动作。
7. **成本口径不变**：live 批准不产生第二次 run，台账里应该只看到一条；如果看到两条，说明 flag 没生效，回退 C。
