## 一句话结论

**最不「流畅」的不是样式，是三处等待加一处无法撤销。** 点「发给 Claude Code」后界面静默等派单跑完（最长 600 秒）；状态靠 5 秒轮询、每次还顺带 spawn 一个 `wsl.exe`（实测 128–165 ms）；终端每 2 秒整包重取最近 300 行而不是流式；「终止」在每张卡上都出现，停的却是全局那一条（在 B 卡点会杀 A 的会话）。本方案按「先去掉等待、再修别扭、最后清债」分六个阶段落地，每阶段独立可交付、可回滚。

## 5.3 阶段一：派单异步化

### 5.3.1 现状与问题

`/api/task/dispatch`（`server/server.mjs:627`）、`/api/task/continue`（`:612`）、`/api/pool/suggest`（`:496`）、`/api/task/explore`（`:658`）、`/api/prompt/optimize`（`:742`）、`/api/task/docs`（`:755`）、`/api/task/split`（`:766`）、`/api/task/optimize`（`:776`）都在 HTTP 请求里 `await dispatch.runDispatch(...)`；`runDispatch` 的 Promise 要等子进程 close（`server/dispatch.mjs:44-101`），`TimeoutSec` 默认 600 秒（`agent/claude-dispatch.ps1:97`）。前端 `dispatchTask` 也是 await 完才 flash + refresh（`web/src/store/useTasks.ts:36-51`）。

### 5.3.2 先分类，再动手（关键）

不是所有 AI 动作都该异步，按「是否需要把结果拿回来展示」分两类：

| 类型 | 接口 | 处理 |
| --- | --- | --- |
| **投递型**（不需要返回值，只要开始） | `/api/task/dispatch`、`/api/task/continue` | 立刻返回，后台跑 |
| **取结果型**（要把文本回填到弹窗/草稿） | `/api/pool/suggest`、`/api/task/docs`、`/api/task/split`、`/api/task/optimize`、`/api/task/explore`、`/api/prompt/optimize` | 第一阶段只加进度反馈（spinner + 预计耗时 + 可离开），**不改契约**；后续可升级成 job 化 |

先做投递型，因为它们占了日常点击的绝大多数，而且改完收益最直接。

### 5.3.3 改法

服务端（`server/server.mjs`，照抄 `/api/pool/push` 已有的异步写法 `:539-548`）：

```js
"/api/task/dispatch": async (b) => {
  const task = dispatch.getTask(b.id);
  if (!task) throw new Error("没有这条任务");
  const run = {
    task: b.task || task.note || task.subject,
    mode: b.mode === "write" ? "write" : "read",
    allow: b.allow || "",
    repo: task.repo,
    taskId: b.id,
    resume: task.sessionId || "",
  };
  dispatch.markStarting(b.id);          // 新增：写 data/pending.json {taskId: startedAt}
  setImmediate(() => {
    dispatch.runDispatch(run)
      .then((r) => {
        if (r && r.session_id) dispatch.setTaskTask(b.id, { sessionId: r.session_id });
        syncBrain(b.id, task.subject, r);
      })
      .catch((err) => syncBrain(b.id, task.subject, { status: "failed", error: err.message }))
      .finally(() => dispatch.clearStarting(b.id));
  });
  return { started: true, taskId: b.id };
}
```

- `markStarting` 写 `data/pending.json`（`{ taskId: {at, kind} }`），`buildState()` 把它并进 `tasks[].starting`，前端据此立刻显示「执行中（启动中）」。
- 不改 `claude-dispatch.ps1`：它本来就会写 `data/running.json`（`:294-304`），接管后 `starting` 清掉即可，不必让 Node 预生成 runId。
- `clearStarting` 放在 `.finally()`，失败也要清，否则永久「启动中」。

前端（`web/src/store/useTasks.ts:36-51`）：

```ts
export async function dispatchTask(t: Task, cont = false) {
  busy.value = t.id;
  try {
    await post(cont ? "/api/task/continue" : "/api/task/dispatch", { id: t.id, task: drafts[t.id] || t.note || t.subject });
    flash("已投递，正在接管…");
    await refresh();      // 立刻拿到 starting/running
    fastPoll(t.id);       // 1 s 一次，最多 15 s，等 running 或 sessionId 出现
  } catch (e: any) { flash(e.message, true); }
  busy.value = "";
}
```

### 5.3.4 必须同时做的：写入串行化（否则会丢更新）

现在所有 `data/*.json` 都是「读全文件 → 改 → 写全文件」（`server/dispatch.mjs:163-170`、`server/pool.mjs:46-58`、`server/docsync.mjs:39-41`）。同步请求里这没问题，一旦写入动作挪到 `setImmediate`/定时器里，两次并发就会互相覆盖（典型症状：刚标完成的任务又被改回 todo）。

做法（`server/store.mjs`，新增约 30 行）：

```js
let chain = Promise.resolve();
export function mutate(file, fn) {
  chain = chain.then(() => {
    const cur = readJson(file, []);
    const next = fn(cur) ?? cur;
    const tmp = file + ".tmp";
    writeFileSync(tmp, JSON.stringify(next, null, 2), "utf8");
    renameSync(tmp, file);          // Windows 上 Node 的 rename 会 REPLACE_EXISTING
    return next;
  }).catch(() => {});
  return chain;
}
```

把 `setTaskTask` / `deleteTask` / `pool.saveTasks` / `docsync.save` 换成 `mutate()`。**这一步不做，阶段一反而比现在更容易丢数据。**

### 5.3.5 风险与回滚

- 返回体从 `{dispatch, session}` 变成 `{started, taskId}`：旧 `web/dist` 不兼容 → 前后端同批构建部署；若只回滚前端，会看到「派单 ?」字样，不会崩。
- 后台任务里的异常不能再冒到 HTTP：所有 `.then/.catch` 都要兜底，否则 `unhandledRejection` 会让 Node 退出（Node 20 默认 `--unhandled-rejections=throw`）。
- 回滚方式：把 `setImmediate` 包回 `await` 即可（一行），`pending.json` 残留无害（前端只在有记录时显示「启动中」，超 5 分钟自动忽略）。

## 5.5 阶段三：终端流式

### 5.5.0 与 6 号的分工（重要）

同目录的 [6_终端页信息表达重构.md](6_终端页信息表达重构.md) 已经把终端页做到了「契约层」：`stream-json` 从「行」升级成「轮 + 动作」、按动作类型渲染、搜索/筛选、两栏布局、回放归档。**那份方案管「终端里显示什么」，本方案的阶段三只管「数据怎么到达前端」，两者不要各写一遍：**

| 归属 | 内容 |
| --- | --- |
| 6 号 | `RawLine` 契约升级、`tool_use`/`tool_result` 配对、轮次归并、截断策略、回放归档、列表/详情布局、搜索筛选 |
| 本方案（5.5.2–5.5.4） | 单条多路复用 SSE（避免连接数打满）、增量追加与 `seq` key、视图保活、跟随最新 |

执行时建议：**先落 5.5 的传输层（1 条流 + 增量 + 保活），再按 6 号重排渲染**。反过来做（先改渲染再改通道）等于把 6 号的渲染逻辑写两遍。

### 5.5.1 现状

`useLifecycle.ts:18-21` 每 2 s 对每个 `termTask` 调 `loadRaw()`；`useTerminal.ts:69-77` 整包替换 `raws[id]`；`TerminalCard.vue:52` 用 `:key="i"` 渲染整段 `<pre>`；视图 `v-if`（`App.vue:32-38`）导致切换即销毁。服务端 `/events/claude`（`server/events.mjs:174-219`）**只 tail 全局最新那个 stream 文件**，且前端从未使用（唯一的 EventSource 是 `store/useWb.ts:8`）。

### 5.5.2 为什么不能「每张卡一条 SSE」

浏览器对同源 HTTP/1.1 并发连接上限是 6 条。现在已有 `/events/workbuddy`（1 条）+ 潜在的 `/events/state`（1 条），再给 8 张终端卡各开一条（`termTasks` 上限 8，`useTerminal.ts:66`）就会撞上限，表现为「某些流永远不响应」，比轮询更难查。

**采用多路复用一条流**：`GET /events/losflow`，消息体带 `taskId`：

```
data: {"kind":"run","taskId":"7","runId":"20261113-141658-f4e3b2","reset":true}
data: {"kind":"line","taskId":"7","seq":123,"line":{"kind":"cmd","text":"$ Bash npm test"}}
data: {"kind":"end","taskId":"7","status":"ok"}
```

服务端实现要点（`server/events.mjs`）：

- 维护 `Map<taskId, {runId, offset}>`；每 700 ms 轮询一次「哪些任务需要推」：本连接订阅的 taskId 集合由前端首帧发来的查询参数决定（`?tasks=1,3,7`），或干脆推所有 `termTasks`（服务端自己算，最多 8 个）。
- 每个 taskId 的 runId：优先 `running.json` 的 `taskId` 匹配，否则取台账里该任务最近一条（`dispatch.latestDispatchFor`，已有）。
- 读 `\\wsl.localhost\<distro>\tmp\cc-<runId>.stream.jsonl`，按 offset 增量读（现有 `streamClaude` 的模式可直接复用），把每行经 `rawLine()` 转成展示行并附 `seq`。
- runId 变了 → 先发 `{kind:"run", reset:true}` 再续推。
- 连接关闭时停掉所有 offset 状态（放 `req.on("close")`）。

前端要点（`web/src/store/useTerminal.ts`）：

- 一条连接放 `useLifecycle`，`termOpen` 里展开的 id 变化时通过 `send`?（SSE 单向）→ 用查询参数重建连接，或服务端推「当前打开集合」以外的最小集合。**推荐**：服务端直接推 `termTasks` 全集（≤8），前端按 `termOpen` 决定要不要渲染，逻辑最简单、连接只有 1 条。
- 收到 `line` 用 `push` 追加（`raws[id].push(line)`），不再整包替换；`seq` 作为 `:key`。
- `reset` 清空该 id 的 `raws`。

### 5.5.3 视图保活与跟随

- `App.vue:31-38` 换成 `<KeepAlive>` 包 5 个 view（docs 的 iframe 也一并受益），或在 `TerminalsView` 外层用 `v-show`。注意 KeepAlive 会保留组件实例，`useLifecycle` 只应挂在根组件（现在就是）。
- `TerminalCard.vue:52` 的 `:key="i"` → `:key="l.seq ?? i"`。
- 「跟随最新」：`useTerminal` 加 `follow` map（默认 true）。`onTermScroll` 里 `scrollHeight - scrollTop - clientHeight > 48` 时置 false；追加行后若 `follow[id]` 为 true 则 `nextTick` 滚到底。`↓ 底部` 按钮点击后恢复 true。现有 `termAtBottom` 逻辑保留，用于控制按钮显隐。

### 5.5.4 验收

- 终端输出逐行出现，单行延迟 ≤ 700 ms；
- 展开 4 张卡时，DevTools → Network 里 SSE 连接数恒为 2（losflow + workbuddy）；
- 切走 30 s 回来，滚动位置、展开态、已渲染行数都不变；
- 手动上翻后新行不再把视图拽回底部，点「↓ 底部」恢复跟随。

## 5.7 阶段五：工作流闭环（三项确认）

**现状**：`pool.json` 有 `confirm: {detail, flow, auth}`（`server/pool.mjs:75`），推入时靠 `confirm.auth` 决定是否自动开工（`server/server.mjs:534`、`server/pool.mjs:184-191`），接口 `/api/pool/toggle` 也在（`:480`）——但 `/app/` 里没有任何勾选入口，全前端搜不到一次调用，只有废弃的 `server/index.html` 会调。**结果 `autoStarted` 永远是空数组，README 承诺的「授权打勾 → 后台自动派给工作 Agent」走不通。**

**改法**（`components/PoolPanel.vue`）：每条池任务下加三个复选（细则 / 流程 / 授权），调 `/api/pool/toggle` 后 `refresh()`；`推入` 按钮旁显示「已授权 → 推入后自动开工」的提示。`pool.mjs` 的 `pushPool` 逻辑不动。

**验收**：勾「授权」→ 推入 → 返回体含 `autoStarted: ["N"]`，任务卡 1 s 内出现「执行中」。

## 5.10 风险与回滚

1. **写入竞态放大**（最高风险）：异步化会让 `setTaskTask` 的读-改-写重叠。必须先落 5.3.4 的 `mutate()` 串行化，再改派单。回滚：`mutate` 可独立保留，不影响旧路径。
2. **后台异常导致 Node 退出**：`setImmediate` 里必须全链路 `catch`。回归信号：日志出现 `UnhandledPromiseRejection`。
3. **SSE 连接数打满**：坚持单条多路复用（5.5.2）。回归信号：某张终端卡长时间停在「等待第一条输出」。
4. **`fs.watch` 在 Windows 上的抖动**：只 watch `dataDir` 非递归 + debounce 200 ms；不 watch `runs/`（派单时写入很频繁）。
5. **KeepAlive 后 `v-if` 语义变化**：`docs` 的 iframe 会一直挂着，`/wiki` 不再重复加载（是改进），但要注意内存；若发现问题，`docs` 单独回到 `v-if`。
6. **返回体变更**：`/app/` 是 `no-store`（`server/server.mjs` 的 `sendJson`），不会拿到旧 JS；但 DSH iframe 可能缓存页面 → 上线后要求 Ctrl+F5，`update.sh` 的产物哈希校验已能验证。

## 5.11 不做的事

- **不引 Pinia**：现有 composable 够用，多一层只是多一处要同步。
- **不引组件库/UI 框架**：单色极简是刻意设计，`style.css` 已统一。
- **不上虚拟滚动**：8 张卡 × 300 行，先解决「整包重取」比虚拟列表划算一个数量级。
- **不改成 WebSocket**：SSE 单向足够，且服务端已经写好一份可复用。
- **不动 `vite.config.ts` 的 `base: "./"`、`outDir`**：`server.mjs` 的 `/app/` 托管与 `update.sh` 的产物哈希校验都依赖它。
- **不把 `claude-dispatch.ps1` 的同步模式改成流式解析**：那是成本控制核心，本方案只在 Node 侧绕开阻塞。
