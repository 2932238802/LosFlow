## 一句话结论

**现象属实，但根因不是「JS 卡死」，是三件事叠在一起：**

1. **接口同步等**：`/api/pool/suggest` 在 HTTP 请求里 `await` 一整次 Claude Code 会话（`server/server.mjs:664-680` 的处理函数 → `server/dispatch.mjs:113` `runDispatch` → 等子进程 `close` 才 resolve），台账实测 **8.1 s / 19.2 s**；超时上限 600 s（`agent/claude-dispatch.ps1:106`），前端没有超时也没有取消。
2. **进度看不见**：这段时间弹层独占全屏（`SheetShell` 锁 `body` 滚动），而唯一的进度条 `RunProgress` 挂在 `<main>` 里（`web/src/App.vue:48`），被 `z-index:50` 的遮罩（`web/src/style.css:204`）整个盖住；提示文字 3.2 s 后自动消失（`web/src/store/useToast.ts:10`）。→ 屏幕上**没有任何东西在动**。
3. **关了还更糟**：拆到一半关弹层，结果直接丢（`openSplit` 清空 `splitList`，`web/src/store/usePool.ts:140`），而 `splitBusy` 要等原请求回来才复位（`:163`）；再点进去按钮全灰、没有任何解释。

所以严格说浏览器主线程没被阻塞（`fetch` 是异步的），你看到的是**「一次模态等待，且没有可见反馈」**。改法：**P0 把进度搬进弹层、允许关掉且结果不丢（2 小时）；P1 服务端 Job 化，请求 200 ms 返回 jobId、后台跑、刷新不丢、同一池子条目不重复花钱（1 天）**；想让 8–19 s 变成 1–3 s，还有个现成但没人调用的直连网关函数可以接（`server/server.mjs:98` `optimizeViaGateway`，全仓 0 个调用点）。

### 8.1.3 实测耗时（来自 `data/claude-ledger.jsonl`，不是估计）

| 时间 | task_id | 动作 | duration_ms | cost_usd | input_tokens |
| --- | --- | --- | --- | --- | --- |
| 15:25:23 | `p1` | `/api/pool/suggest` | **19218** | 0.126 | — |
| 19:12:45 | `p4` | `/api/pool/suggest` | **8138** | 0.114 | 21290 |

同一条链路上的「优化提示词」（`/api/prompt/optimize`）10 次：**3.6–15.5 s**（例如 15:48:09 15523 ms、16:07:34 5751 ms）。慢的原因不是网络，是**每次都是新会话**：没有 `resume`，每次冷启动都要重新装 ~21K input tokens 的上下文（p4 的 `input_tokens: 21290`），再生成 800 多个字符的 JSON。`p1` 那 19 s 大概是首次冷启动 / 并发排队（同一时段还有别的派单）。

**上界是 600 s**：WSL 起不来、网关 401、`start_claude_code_jz` 卡住时，请求会一直挂着，界面没有任何「取消」入口。

### 8.1.4 顺带核到的 3 件事（同一条链路）

1. **拆分把自己当成了正式派单。** `runDispatch` 会写 `data/running.json`、WSL `/tmp/cc-<runId>.pid`、台账一行、`data/runs/<runId>.json`（实测 p4 → `data/runs/20261113-191235-d80f25.json`，209 KB）、`data/streams/*.jsonl`。后果：
   - 终端页头部「N 个会话正在跑」按 WSL 活 pid 数（`server.mjs:411` `terminalRuns` → `useTerminal.ts:49`），拆一次会短暂多算一个；
   - `claude-dispatch.ps1:180` 在启动时 `Remove-Item running.json`：**真派单正在跑的时候点拆分，会把全局那条 running 摘掉**（卡片状态还有 pid+台账兜底，但「旧接口兼容」那条路会短暂失灵）。
2. **`/api/task/split` + `web/src/store/useTasks.ts:221 splitTask` 是死代码**：前端没有任何调用点，实际只有池子的 `/api/pool/suggest`。`docs/api.md:36` 还写着「取结果型，仍阻塞等结果」——这句话现在等于归档了现状，要跟着改。
3. **`optimizeViaGateway`（`server/server.mjs:111-136`）写完了没人调用**（全仓 0 个调用点，只有文档提过）：它就是「不启 Claude Code 会话、直接 curl 网关要一段文本」，是方案 C 的现成基础。

## 目标

1. 点「让 AI 拆」后 1 s 内仍能操作驾驶舱（切页、看别的池子条目、关弹层）；
2. 拆分在后台跑，**切页 / 关弹层 / 刷新页面都不丢结果**；
3. 同一条池子条目在跑的时候再点，**不产生第二次花费**；
4. 失败 / 超时有明确文案（不再无限转圈）。

## 方案

### A（推荐主案）服务端 Job 化：请求立刻返回 jobId

**接口契约**

| 接口 | 入参 | 返回 | 说明 |
| --- | --- | --- | --- |
| `POST /api/pool/suggest` | `{id, prompt?}` | `{jobId, reused}`，200 ms 内 | 已有同 key 的 running job → 返回同一个 jobId（`reused: true`） |
| `GET /api/job?id=<jobId>` | — | `{id, kind, key, status, label, at, startedAt, elapsedMs, result?, error?, cost?}` | `status`: `running` / `ok` / `failed` |
| `POST /api/job/cancel` | `{id}` | `{stopped}` | 复用 `dispatch.stopRun(runId)`，可选 |

**服务端**：新增 `server/jobs.mjs`（约 80 行），照 `pool.mjs` / `dispatch.mjs` 现有风格：

```js
// data/jobs/<jobId>.json：{id,kind,key,label,status,at,startedAt,doneAt,result,error,cost}
export function startJob({ kind, key, label, run }) {
  const running = findRunning(kind, key);
  if (running) return { id: running.id, reused: true };   // 幂等：连点 / 关掉再点都只有一份花费
  const id = "j-" + Date.now().toString(36) + Math.random().toString(36).slice(2, 6);
  const rec = { id, kind, key, label, status: "running", at: Date.now(), startedAt: Date.now() };
  save(rec);
  setImmediate(async () => {
    try {
      const r = await run();
      save({ ...rec, status: "ok", doneAt: Date.now(), result: r.result || "", cost: r.cost_usd || 0 });
    } catch (e) {
      save({ ...rec, status: "failed", doneAt: Date.now(), error: String(e.message || e) });  // 失败也写盘，前端一定有终态
    }
  });
  return { id, reused: false };
}
```

- 落盘 `data/jobs/`，`purgeHistory` 里顺带清 7 天（跟 `runs` / `streams` 一个口径）；
- 启动时把遗留的 `running` 改判 `failed`（服务重启不在界面上装死；
  和 `dispatch.prunePending` 一个思路，`server.mjs:1145` 旁边加一行）；
- `pool.suggest` 的 prompt 拼装原样搬进 `buildSplitPrompt(item, extra)`，payload 不动。

**前端**：新增 `web/src/store/useJobs.ts`（约 60 行）

```ts
const jobs = reactive<Record<string, Job>>({});
export async function watchJob(id: string, onDone: (j: Job) => void) {
  const tick = async () => {
    const j = await getJSON(`/api/job?id=${id}`);
    jobs[j.id] = j;
    if (j.status === "running") {
      timer = setTimeout(tick, document.hidden ? 5000 : 1000);  // 后台降频，别在看不见的标签页里打点
    } else onDone(j);
  };
  tick();
}
```

- 结果解析复用现有逻辑（`usePool.ts:151-158` 的 `match(/\[[\s\S]*\]/)` + `JSON.parse`），只搬不改；
- `splitList` 由 job 终态驱动，不再由「这一次 await」驱动；
- 「拆分中」状态出现在**池子行**上（`PoolPanel.vue`），所以关掉弹层也看得见。

**UI 改动**

### B（过渡案，2 小时）纯前端：先让它「看起来不卡」

零接口变更，只改前端 4 处：

1. **进度搬进弹层**：把 `RunProgress` 里「label + 已用秒数」抽成 `useElapsed()`，`SplitDialog` 里直接渲染；同时给 `.overlay` 之上的 toast 提 z-index（或拆分期间把 `.runprog` 定位到 `position:fixed; z-index:60`）。
2. **允许关掉**：`aiSplit` 的 promise 挂到模块级 `splitJob = ref<{id, startedAt} | null>`，`finally` 里 `flash("拆分结果已就绪")`；关闭弹层不清 `splitList`，池子行显示「有拆分结果」。
3. **加超时**：`web/src/api.ts:8-16` 的 `post` 加 `AbortController`（90 s），超时文案「拆分超时：WSL 可能没起来，看终端页/设置页」。
4. **失败不留灰按钮**：`splitBusy` 在 `closeSplit` 时不清，但按钮 `title` 写清「上一次拆分还在跑」。

代价（写清楚，别让人误以为够了）：**刷新即丢**、仍占一个长 HTTP 连接、不能两个池子条目同时拆。

### C（治本延迟）拆分不走 CC 会话，直接问网关

`optimizeViaGateway`（`server.mjs:111-136`）已经会：把请求体写临时文件 → 在 WSL 里 `eval` 出 `ANTHROPIC_BASE_URL / KEY / MODEL` → `curl --max-time 90` 打 `/v1/messages`。它现在缺的只是：**响应解析**（取 `content[0].text`）、错误分型、以及一个调用点。

改法：

```js
// server/llm.mjs（把 optimizeViaGateway 提升成通用函数）
export async function llmComplete({ system, prompt, maxTokens = 1200 }) {
  const r = await viaGateway({ system, prompt, maxTokens });
  if (r.ok) return { text: parseAnthropicText(r.raw), cost: 0 };
  throw new Error(`网关失败：${firstLine(r.err || r.raw)}`);   // 调用方决定要不要回落 CC
}
```

- `/api/pool/suggest` 默认走 `llmComplete`，抛错 → 回落 `dispatch.runDispatch`（保命，不会因为 WSL 停就完全不能拆）；
- 收益：预计 **1–3 s**（同网关的短调用量级，未实测本路径），且**不再**写 `running.json` / 台账 / `runs` / `streams`、不占终端计数、没有 21K 冷启动 input；
- 风险 1：网关三件套靠 `grep '^export ANTHROPIC_' /usr/bin/start_claude_code_jz`（`server.mjs:125`），WSL 停就失效（doc 7 已登记同一问题）——建议顺手把这套配置挪进 `losflow.config.json`；
- 风险 2：拆分是纯文本改写（prompt 里只有标题/说明 + JSON 格式要求），不需要工具和仓库上下文，质量风险低；但仍按「同一任务拆两次」做 A/B，留开关 `aiSplitEngine: "gateway" | "claude-code"`（默认 `gateway`，试一周，不行一键切回）。

## 验收标准（逐条可验）

1. 点「让 AI 拆」→ **1 s 内**能切到「终端」页、能点开另一条任务卡；池子那一行出现 `拆分中 0s→6s`（每秒在涨）。
2. 拆分中关掉弹层 → 池子行仍显示「拆分中」；完成后变「有拆分结果（N 条）· 查看」，点开直接看到结果，**不重新花费**。
3. 拆分中刷新浏览器（F5）→ 回来后仍显示「拆分中」，完成后同样能查看结果（P1 起）。
4. 同一条池子条目在 `running` 时连点 5 次 → `data/claude-ledger.jsonl` 只多 **1** 行（成本证据）。
5. 把 WSL 停掉再点拆分 → 90 s 内给出明确错误（不是 600 s 后给一个 `timeout`），弹层按钮恢复可点。
6. 拆分进行中，任务页/终端页的既有操作（切页、展开卡、看会话）不受影响；终端页「N 个会话正在跑」**不**因为拆分 +1（P2 起；P1 阶段接受 +1，但在池子行标明）。
7. `npm run build && npm run typecheck && npm run smoke` 全绿；`docs/api.md` 的 `/api/pool/suggest`、`/api/job`、`/api/task/split`（删或标废弃）同步更新。

## 工作量与风险

| 项 | 量 | 备注 |
| --- | --- | --- |
| `server/jobs.mjs` + 路由 | ~100 行 | 照 `pool.mjs` 风格，无新依赖 |
| `web/src/store/useJobs.ts` | ~60 行 | 轮询 + 后台降频 |
| `SplitDialog` / `PoolPanel` / `usePool` 改造 | ~80 行 | 结果驱动替代 await 驱动 |
| `llm.mjs` + 引擎开关（P2） | ~70 行 | 复用 `optimizeViaGateway` |
| 测试 | 复用 `scripts/smoke.mjs`，补 3 条：幂等、终态、超时 | — |

**风险**

1. **旧构建不兼容**：`/api/pool/suggest` 返回体从 `{dispatch, raw}` 变 `{jobId}`，`web/dist` 必须同批构建（跟 doc 5 的派单异步化同一个坑）。要留后路就加 `?sync=1` 走旧逻辑一版，下个版本删。
2. **job 泄漏**：进程被强杀时 `data/jobs/*.json` 会留 `running`。启动时统一改判 `failed`（`server.mjs:1145` 旁边加一行 `jobs.reap()`），并在 `GET /api/job` 里对超过 `claudeTimeoutSec + 60 s` 的 `running` 直接判失败。
3. **`data/jobs/` 增长**：结果里存 `raw` 全文（拆分 JSON 约 1 KB，优化文本约 2 KB），7 天清理足够；不要往 `/api/state` 里塞 job 列表（P1 用独立 `GET /api/job`，别把 5 s 轮询的 payload 撑大）。
4. **幂等键冲突**：`key = pool id`。用户改了 prompt 想重拆时要能绕过幂等 → 前端「重新拆」按钮带 `force:true`，或 job 终态后自然失效（推荐后者，简单）。
5. **回滚**：P1 回滚 = 前端改回 `await post(...)`、服务端路由改回同步（两处，各 5 行）；`data/jobs/` 残留无害。

## 不做的事

- 不引入 WebSocket / 消息队列 / Redis / job 框架依赖（本地单人工具，1 s 轮询足够）；
- 不做假百分比进度（只有「已用 N 秒 + 阶段名」）；
- 不动 `claude-dispatch.ps1` 的 600 s 超时（P2 走网关后这条链路与拆分解耦）；
- 不为拆分单独做一条 SSE（`/events/losflow` 现在是终端专用的多路复用流，往里加 job 类型收益不抵改动）。
