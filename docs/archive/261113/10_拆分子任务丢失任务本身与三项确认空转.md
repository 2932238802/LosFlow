## 一、结论先说

**两处现象都属实，而且是同一条链路上的三个断点，不是三个独立的小毛病：**

1. **拆分只产出「标题级」结果，没有「正文级」字段。** 输出契约是 `[{title, owner, reason}]`，`applySplit` 又写死 `note: ""`。子任务进池那一刻就没有任务本身，推入后派给 Claude Code 的正文里只剩「优先级：… / 腾讯文档…」两行簿记，没有需求。
2. **三项确认里只有「授权」接了线，另外两个从建池起就是死字段；拆分还会把父条目已做的确认清零。** 拆 4 条 = 12 个勾，其中 8 个永远无效，剩下 4 个要重新勾；父上勾过的「授权」也不继承，所以「授权 → 推入自动开工」在拆分场景下永远走不通。
3. **「拆分 SKILL」只是半可改。** 能改的只有一段单行 system 提示；真正的 JSON 契约（字段白名单）、说明/补充要求段落、输出约束全硬编码在路由里。改模板改不出 `note` 字段，也加不了验收标准；而且没有校验、没有版本、没有预览，改坏了直接进 prompt。

一句话：**拆一次 = N 个只有标题的空壳 + 要重勾一遍的确认 + 父正文被留在池子里（父被删就彻底丢）。** 存量 `p9`/`p10` 就是这两条的空壳，正文已经丢了。

## 四、方案

### 4.1 四条原则

1. **没有任务本身，不算拆出一条子任务。** 子任务入池前 `note` 必填；后端也校验，不靠前端自觉。
2. **确认只做一次，在父条目上做。** 拆分继承确认结果，子条目只读展示「继承自谁、授权没授权」，不再逐条勾。
3. **SKILL 是文件，不是文本框。** 可编辑、可 diff、可回滚；输出字段由 SKILL 声明，路由不再写死 schema。
4. **拆分不产生孤儿。** 父记录 `children`；删父时提示还有几条子条目；子条目始终能回到父正文。

### 4.2 方案 A（推荐，P0，0.5–1 天）：把「任务本身」变成拆分的必填产物

**A1 输出契约加 `note`**

```json
[{"title":"子任务标题","owner":"claude-code 或 workbuddy","reason":"为什么单独拆","note":"这条子任务的任务本身"}]
```

`note` 的硬规则（写进 SKILL，不只写在路由里）：

- 看完 `note` 就能开工，**不依赖父任务上下文**；
- 父任务说明里已经写好的要求，**原样搬进对应子任务的 note**，不许概括、不许省略路径/数字/行号（这条直接对应「父亲任务本身就给子任务写好的任务本身」）；
- 写清四件事：做什么 / 照哪做 / 怎么验 / 要什么回执；
- 一句话一行，不用未转义的 JSON 特殊字符（配合 C 的容错解析）；
- 子任务之间不要有先后依赖，3–6 条，粒度适中。

**A2 服务端拼 prompt**（替换 `/api/pool/suggest` 里那段数组）：

```js
const prompt = [
  tpl.splitSystem,                       // 见 4.3：SKILL 正文
  "",
  `任务：${item.title}`,
  item.note ? `说明：\n${item.note}` : "",
  b.prompt ? `补充要求：\n${b.prompt}` : "",
  "",
  "按 SKILL 规定的字段输出严格 JSON 数组，不要解释、不要代码块：",
  schemaHint,                            // 由 fields 生成，如 [{title,owner,reason,note}]
].filter(Boolean).join("\n");
```

**A3 前端可编辑正文**

- `splitList` 加 `note`；`SplitDialog` 每行改成：勾选 + 标题 + owner 下拉 + `note` 文本域（`rows=3`）+ 「沿用父任务正文」小按钮；`reason` 用灰色小字显示在标题下。
- 勾选框在 `note.trim()` 为空时禁用，并提示「先补任务本身」；「加入池子」按钮在任一勾选项没有正文时禁用。

**A4 `applySplit` 落库**

```js
const note = String(s.note || "").trim() || String(it.note || "").trim();
if (!note) throw new Error("子任务缺少任务本身（note）：" + title);
...
note,
confirm: { ...(it.confirm || {}), detail: false, flow: false, auth: false }, // 或保留三条，见 4.5
children: [], parent: id, owner: s.owner, stage: "pool",
```

拆完补两行：`it.children.push(...created.map(c => c.id))`、`it.stage = "split"`；`splitCount` 保留。

**A5 推入不再污染正文**

- `note` 只放正文；`priority` 已有独立字段，不要再拼「优先级：X」进正文；
- 「腾讯文档那一行由同步队列异步写入」这句只在 `docsync` 任务里出现，不写进 `note`；
- `pushPool` 遇到 `!note.trim()` 直接报错「这条没有任务本身，先补正文（池子卡片 → 编辑正文）」；
- `docsync.enqueue({ note: t.note })` —— 用子条目正文，不要再用 `it.note`。

**A6 界面语义修**

- 子条目卡片（`it.parent` 存在）：不渲染三个勾，改为一行只读「继承自 `p4` · 细则✓ 流程✓ 授权✓」+ 正文前两行摘要 + 「编辑正文」。
- 「已拆 N」读 `children.length`；推入后另显示「已推 N」，不要复用同一个字段。
- 父条目推入前，如果 `children.length > 0`，提示「这条已拆成 N 条子任务，要一起推入还是只推父？」——避免把父正文再建一遍。

**A7 补一条改正文的接口（救存量）**

```
POST /api/pool/note { id, note }
→ pool.setNote({id, note})：读改写，写 note + updatedAt，返回 { id, note }
```

池子卡片加「编辑正文」内联编辑（失焦保存）。`p9`/`p10` 用这个入口把正文补回去，不用删了重拆。

**A8 存量数据处理**

- `p9`/`p10`：人工补正文（从 `p4` 的原始正文里摘对应段落——`p4` 的拆分配偶还在 `data/runs/20261113-191235-d80f25.json` 的 `task` 里，可作来源）；
- `parent:"p4"` 保留，作为历史标记；界面显示「父条目已删除」而不是报错；
- 不写迁移脚本自动重建正文（原文不在，猜出来的正文比空更危险）。

### 4.3 方案 B（P1，0.5 天）：SKILL 文件化，字段可改

**B1 位置**：`docs/skills/split.md`、`docs/skills/optimize.md`。放在 `docs/` 下而不是 `data/`，因为要跟着仓库 review、能 diff、能回滚。

**B2 格式**（frontmatter 决定契约，正文是系统提示）：

```markdown
---
name: split
output: json-array
fields: [title, owner, reason, note]
---
你是任务拆分助手。把一条任务拆成 3-6 条可独立执行、可独立验收的子任务。

硬规则：
1. 每条子任务必须自带「任务本身」（note）……
2. 父任务说明里已经写好的要求，原样搬进对应子任务的 note，不许概括……
3. note 写清：做什么 / 照哪做 / 怎么验 / 要什么回执……
4. owner 只能是 claude-code 或 workbuddy。
```

**B3 加载与渲染**：启动时读文件（缺文件 → 写内置默认），路由只负责把 `{{title}} {{note}} {{extra}} {{schema}}` 填进去。`schema` 由 `fields` 生成；字段白名单外的内容直接拒绝，保证 JSON 可解析。

**B4 保存**：`POST /api/skills { name, content }` → 校验 frontmatter（`output` 合法、`fields` 是白名单子集）→ 写文件 → 旧版备份到 `docs/skills/.history/<name>-<时间戳>.md`。校验失败返回 400 + 具体哪一行。

**B5 UI**：`TemplateDialog` 改成「提示词 SKILL」：两个 tab（拆分 / 优化），显示文件路径、当前字段、**最终 prompt 预览**、「恢复默认」「保存」。保存即写文件，刷新不丢。

## 五、验收标准（逐条可验）

1. 用 `p4` 的正文重拆一次：4 条子条目 `note` 全部非空，且每条含原文里的路径/编号（不能是概括句）；池子卡片显示正文前两行。
2. 勾选一条 `note` 为空的子任务时无法勾上；绕过前端直接 `POST /api/pool/apply` 带空 `note` → 400，且错误信息带子任务标题。
3. 推入子条目后：`data/Vesta.tasks.json` 里该条 `note` 以正文开头（不含「优先级：」「腾讯文档那一行」）；`data/claude-ledger.jsonl` 对应行的 `task_preview` 里能看到需求原文，而不是簿记行。
4. 父条目勾「授权执行」→ 拆分 → 子条目显示「继承自 … · 已授权」→ 推入 → 返回的 `autoStarted` 非空，终端页出现这条的会话。
5. 父条目拆分后：池子行显示「已拆 N」（N = `children.length`），`stage = "split"`；再点推入会被提示「已拆成 N 条」，不会静默按父标题再建一条。
6. 改 `docs/skills/split.md` 的正文（例如加一句「note 至少 3 句」），不重启也能在下一次拆分生效；把 frontmatter 的 `fields` 写成 `[title, note]` → 保存后拆出结果只有两个字段，且前端不报错。
7. 把 `split.md` 的 frontmatter 改坏（缺 `name`）→ 保存返回 400，提示具体行；文件内容不变。
8. `p9`/`p10` 在池子卡片上「编辑正文」→ 保存 → 刷新后仍在；推入后任务表有正文。
9. 拆分输出里故意混入未转义换行 → 前端提示「第 N 条不合法」，其余条目仍可选择入池（P2 起）。
10. `npm run typecheck && npm run build && npm run smoke` 全绿；`docs/api.md`（`/api/pool/suggest`、`/api/pool/note`、`/api/skills`）、`docs/architecture.md`（关键契约）、`web/wiki.md`（拆分按钮说明）同步更新；`README.md`/`wiki.md` 删掉不存在的 `cc:`/`wb:` 口径。

## 六、工作量与风险

| 项 | 量 | 备注 |
| --- | --- | --- |
| `/api/pool/suggest` 契约 + prompt | ~40 行 | 顺带把 schema 从 `fields` 生成 |
| `pool.mjs`：applySplit / pushPool / setNote | ~60 行 | 改的是现有函数，无新依赖 |

| 测试 | 复用 `scripts/smoke.mjs` | 补 3 条：空 note 拒绝、继承 auth、skills 校验 |

**风险**

1. **JSON 内嵌换行/引号**：`note` 一定会有换行。要么要求统一 `\n` 转义，要么前端不用 `JSON.parse` 整段、改成逐对象扫描；C 的容错解析是兜底，不是替代。
2. **成本上升**：`note` 从 0 字变 200–600 字/条，拆分会话的输出和后续派单的输入都涨；`budget 0.35` 可能不够，建议先提到 0.5 并观察 3 次。
3. **旧数据兼容**：老 `pool.json` 没有 `note`/`confirm`/`parent` 时按缺省处理（`confirm` 视为全 false、`note` 视为空）；`pushTaskId` 与新的 `children` 并存一版，别一次改两个字段。
4. **并发改动**：`server/server.mjs` 正在被 7 号方案改（env 分流、`metaChat`），落地时按「路由键」小块合，不要整文件覆盖；`usePool.ts` 也在被 5/6 号方案动进度条，先 rebase 再改。
5. **删父条目**：现在删父不提示子（`p9`/`p10` 就是这么来的）。建议删除前弹「还有 N 条子任务，删了会失去来源」，不级联删。
6. **「确认继承」的误读**：父没勾授权时子也不自动开工，这是正确行为；卡片要写清「继承：未授权」，否则会被当成新 bug。

## 七、不做的事

- 不做多级拆分（子任务再拆）——先把一级正文做对；
- 不让 AI 拆分直接入池，仍然要人看一眼正文、勾选、可改；

- 不自动重写 `p9`/`p10` 的正文（原文已丢，编出来的比空更危险）；
- 不为拆分单独加 SSE / 队列，沿用 8 号方案已有的 job 化路径（若采纳）。
