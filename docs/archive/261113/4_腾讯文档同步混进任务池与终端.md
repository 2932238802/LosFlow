## 一句话结论

「往腾讯文档任务表写一行」本来只是 docsync 异步队列里的一个默认后台动作（WorkBuddy 的活），但代码里另有一条「把它建成普通任务」的路，而且这条路是**默认开着**的：`checkAutoCleanup()` 每完成 5 条任务就 `pool.createTask("整理腾讯文档主表…")`，手动建任务入口（`taskboard.ps1 -Add` / wb-bridge `add_task`）也不拦——现状 `data/Vesta.tasks.json` 里的 `#5 在腾讯文档任务表追加一行：版本号同步与工程元数据规范` 就是这么来的。任务模型里没有「文档同步」这个类别，于是它和正常开发任务一样进「任务」列表；派单又默认拿 `task.note` 当提示词，整段腾讯文档操作指令就原样落进终端，Claude Code 还照着跑了 3 次（每次约 $0.05）。

## 现象

- 任务池里反复出现以「在腾讯文档任务表追加一行：……」开头的条目；展开后整段是腾讯文档的字段值与硬约束。
- 点「发给 Claude Code」后，终端顶部提示词就是那段文档指令。`D:\PROJECT\Ds\brain\task-journal.md` 记录 `#5` 在 2026-11-13 15:04–15:05 连跑 3 次，各 1 轮，$0.054 / $0.058 / $0.064。
- 杰哥口径：写文档是默认行为，不该进终端。

## 核实证据（2026-11-13，只读核对）

### 1. 现存条目长什么样：`data/Vesta.tasks.json` `#5`

| 字段 | 值 |
| --- | --- |
| `subject` | 在腾讯文档任务表追加一行：版本号同步与工程元数据规范 |
| `owner` | `workbuddy` |
| `status` | `done`（WorkBuddy 已真的写进去了，`evidence` 里有逐格读回校验） |
| `note` | 完整的 append-row 指令：表格 URL / 主表 tab / 逐字段取值 / 4 条硬约束 / `report_task` 回填要求 |

**它不是「推入」生成的**：`data/pool.json` 里没有对应条目；`#5` 也没有 `kind` / `repo` 字段。而 `pool.pushPool()`（`server/pool.mjs:184-227`）写任务时必带 `kind`，并在 `note` 里拼上「腾讯文档那一行由同步队列异步写入，不用手动补。」的尾巴——`#5` 两样都没有。所以 `#5` 只能来自**直接建任务**的入口：`agent/taskboard.ps1 -Add`（`80-99`，只写 id/subject/owner/note/status）或 wb-bridge 的 `add_task`（`server.mjs:205-235`，同样只写这几个字段）。`pool.createTask()` 会写 `kind`，也可排除。

### 2. 它为什么出现在「任务」列表

- `web/src/App.vue:164`：`openTasks = tasks.filter(t => t.status !== "done")`，任务页就渲染这个列表。
- 卡片展开后 `App.vue:698-701`：「执行说明 · 发给 WorkBuddy（只读）」+ `<pre class="note-pre">{{ t.note || t.subject }}</pre>`，把整段文档指令铺在卡片里。
- `Task` 类型（`App.vue:6-12`）没有「这条是文档同步活」之类的字段，UI 无从分流。

### 3. 它为什么会进终端

- `server/server.mjs:632`（`/api/task/dispatch`）与 `:617`（`/api/task/continue`）的默认提示词都是 `b.task || task.note || task.subject`。文档指令就躺在 `note` 里，一点派单，整段进终端，没有任何「这条是文档活、别发给 CC」的拦截。
- 终端页只按会话过滤（`App.vue:206-208`：有 `sessionId` / 正在跑 / 有 `run` 就上榜），跑过一次就长期留在终端页。
- 结果：Claude Code 在 Vesta 仓库里照着一段它根本执行不了的腾讯文档指令干活，白花 token（3 次约 $0.18），还会把终端刷成文档操作手册。

### 4. 「默认行为」这半句在代码里确实成立

- `server/server.mjs:177-202` `checkAutoCleanup()`：拿 `maintenance.json` 的阈值（默认 `5`），累计到阈值就

  ```js
  pool.createTask({
    title: "整理腾讯文档主表：把已完成/已搁置的行移到归档",
    owner: "workbuddy",
    note: cleanupNote(),   // 整段腾讯文档操作指令
    kind: "company",
  });
  ```

- 这不是隐藏开关：`_progress/maintenance.json` 里 `threshold: 5`、`lastAt: 2026-11-13T07:31:26.196Z`（本地 15:31），说明当天确实自动建过一次。
- `server/server.mjs:515-529` 的「整理主表」按钮走同一条造任务路径。
- 所以即使没人手动建，「任务池里冒出一条腾讯文档指令」也会周期性发生。

### 5. 本来的设计：这件事就不该有任务行

- 推入时 `pool.pushPool()` 入队（`server/pool.mjs:213-216`：`docsync.enqueue(...)`）；
- 标记完成时 `server/server.mjs:721` 入队一条 `update-row` 回填（`enqueueBackfill`）；
- 队列由 `agent/wb-bridge/server.mjs:160-204` 的 `next_docsync` / `report_docsync` 消费；
- `README.md:10-11` 与 `web/wiki.md:68-84` 写得很清楚：**任务本体派给 Claude Code，文档那一行异步入队、WorkBuddy 有空再写**。

也就是说：文档行有自己的一条异步通道，根本不需要、也不应该在任务表里占一行。

## 根因

1. **两条通道并存**：正确通道是 docsync 队列；错误通道是「建一条普通任务」，而 `checkAutoCleanup` 把错误通道设成了默认行为。
2. **任务模型缺类别**：`Task` 上没有 `docOnly` / `kind: "docsync"` 之类的标记，`openTasks`、终端卡、阶段推断、派单全都按普通任务处理。
3. **派单默认取 `note`**：这个设计是为开发任务准备的（note 就是发给 CC 的提示词），碰上文档类任务就把操作指令泄漏进终端。

## 期望（杰哥口径，作为验收口径）

- 写腾讯文档（append-row / update-row / 整理主表）只走 docsync → WorkBuddy；不建任务、不进任务池、不进终端、不派给 Claude Code。
- 任务池与终端只承载「要动代码或读代码」的活。
